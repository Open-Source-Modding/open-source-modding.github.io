2. Container-level notes​

  • Standard DBPF 1.0 exactly as already handled by addons/dbpf/DBPF.gd; the engine's QFS decompressor and DIR handling load every subfile in this save without error.
  • Almost every savegame subfile lives in group 0x299B2D1B (121 of 179 entries). The exceptions: LTEXTs (0x6AAEE931/32 name/mayor, 0x4A2482BB thumbnail labels), PNG thumbnails (0x4A2482BB), terrain (0xE98F9525), the region-view record (0xCA027EE1) and a handful of singletons.
  • Savegame records follow SC4's standard serialization: u32 size, u32 CRC, u32 memory address, then a version and class-specific payload. 120 of the 133 types chain cleanly as size-prefixed record arrays (verified while counting the records above).
  • Several network subfiles are absent from this save — network subfile 2 (0xCA16374F, bridges/elevated), the tunnel subfile (0x8A4BD52B), the prebuilt network (0x49C1A034) and the power-line pair (0xC9C05C5D / 0x09C05C6A) — consistent with a flat tutorial city with no bridges, tunnels or long-distance power. Other shipped saves do have them: see §4.4.

3. Implementation status in OpenSC4 (summary)​

Implemented today (15 of the 133 types present): building/prop/flora occupants, lots, lot base textures, terrain altitudes (main map only), region-view stats, PNG thumbnails, LTEXT, the DIR directory, and — as of 2026-08-06 — the whole of §4.4: ground networks, pipes, the network index, lot foundations and retaining walls, plus the power-line and bridge subfiles that occur in other saves. In short: everything the city renderer needs to draw a complete city, and nothing of the simulation.

Prop rendering was completed later the same day. 413 of this save's 69,431 prop occupants reference no 3D model at all — they are 2D sprites, and were being silently dropped; §8 has the format and the fix. The 2,339 props still unplaced are a different problem: they do name an S3D model, but no zoom/rotation variant of it exists in the DATs we load.

Not implemented (present in this save): the item index, zone developer/manager, tract developer, all 136 SimGrid layers, every simulator/manager state blob, budget (departments, line items, taxes), the ~20 ordinances, historical graph data, advice state, and the COM-serializer registry.

Engine scaffolding still unfed: CityView/ClassDefinitions/ (NetGraphNode, NetGraphEdge, NetTile, TransitTile) models a transit-network graph. The §4.4 parsers give it geometry but not connectivity — that needs SC4Path (0x296678F7), which has no parser. Note NeworkGraph.gd (filename typo intentional) is dead and internally inconsistent (tile.networedges vs tile.networkedges); treat it as a sketch, not an API.

Also worth noting: the region UI derives the displayed city name from the filename (RegionCityView.gd:22), while the save carries properly localized name/mayor LTEXTs.

The key structural finding. A ground-network record does not need the RUL tile-shape rules to be evaluated. SC4 resolved them when the tile was built and saved the answer: each record carries its four deck corners with position, texture coordinate and baked lighting colour, plus the already-chosen texture id. Rendering is therefore a direct read — which is why sloped roads, diagonals and level crossings came out right without touching RULSubfile.gd. Verified layout:

u32 size, u32 crc, u32 mem, u16 major(8), u16 minor(4)
u16 zot, u8 ?, u8 appearance      (bit 0 = present in city, bit 6 = burnt)
u32 0xC772BF98                    family marker, constant
tract: u8 minX, minZ, maxX, maxZ, u16 xTractSize, zTractSize
u32 sgpropCount + sgprops[]
u32 GID, u32 TID, u32 IID         all zero on ground networks
u8 ?
f32 position x, y, z              metres, tile centre
4 x vertex { f32 x,y,z,u,v; u8 r,g,b,a }        24 bytes each, odd-aligned
u32 textureId                     FSH family; high byte = network family per RULSubfile.gd
u8  wealthTexture
u32 baseTexture                   FSH family for the sidewalk/ground underneath
u8  orientation
u8 x2 ?
u8  crossingCount-1
crossings[] { u8 networkType, west, north, east, south }
u32 wallCount + walls[] { u32 texture, vertex }
bbox: 6 f32 grouped BY AXIS (minX, maxX, minY, maxY, minZ, maxZ)
u32 constructionStates, u32 alternatePathId, 3 x u32 ?, u64 demolishingCosts

networkType: 0 Road · 1 Rail · 2 Maxis El Highway · 3 Street · 4 Pipe · 5 Powerline · 6 Avenue · 7 Subway · 8 Light Rail · 9 Monorail · 10 One-Way Road · 11 Dirt Road.

Textures resolve at TGI (0x7AB50E44, 0x1ABE787D, textureId + zoom) for zoom 0..4 — the same scheme TransitTiles.gd already used. All 36 distinct texture ids in Big City Tutorial resolve with all five zoom variants present.

Foundations and retaining walls store a placement block that no community parser documents. It was decoded here as f32 x, y, z, size_x, height, size_z (metres), at record offset 0x38 for foundations and 0x48 for walls. Evidence: 100% of the 1,245 walls and 2,510 foundations in Big City Tutorial then have their centre on a lot-covered tile (the x/z transpose gives ~55%), and the median of y − terrain altitude is exactly 0.00 m. Their exemplars carry no model for most records — instead a five-entry list of FSH zoom variants plus the world size one repeat covers (0x295961F2/0x295961F3 for walls, 0x68FCFF37/0xC911EDA0 for foundations), i.e. SC4 stretches a texture over a box. A minority carry an RKT1 S3D model instead.

What is still undecoded. The network index's per-entry payload: between consecutive {tile_number, mem, subfile_type} triples sits a variable-length block nobody has decoded, and SC4Parser's own attempt cannot keep the cursor aligned. NetworkIndexSubfile.gd resynchronises by scanning for the next triple instead, which recovers exactly the declared reference count in every populated save. What tile_number means is also open — it is not a row-major tile index (both that and its transpose match only about half the entries against the actual tile coordinates of the ground-network records).

5. What implementing the rest would unlock​

Done — network subfiles (§4.4), 2026-08-06. Ground networks, pipes, the network index, lot foundations and retaining walls all load and render, as do the power-line and bridge subfiles that appear in other saves. What it did not unlock, contrary to what the previous version of this list assumed: the CityView/ClassDefinitions/ graph classes still have no input. A graph needs connectivity, and these subfiles carry only geometry — the connectivity lives in SC4Path, now item 1 below.

Done — 2D sprite props (§8), 2026-08-06. Every prop occupant in this save that has artwork in the DATs now draws. What remains on the prop side is not a format gap: 2,339 occupants name an S3D model whose zoom/rotation variant is missing from the six DATs the loader opens, which is a question of which files we load, not of parsing.

Remaining, ordered by likely value to OpenSC4:

  1. SC4Path (0x296678F7) — the per-tile vehicle paths. This is now the single missing piece between "the network is drawn" and "the network is a graph": it would feed TransitTile.set_tile_paths() (a stub returning {}) and thence NetworkGraph, and it is the prerequisite for any traffic simulation or route display. Note it is a DAT type, not a savegame type — the paths live in the game's own data files, keyed per network piece.
  2. SimGrids (§4.5) — the record header is fully decoded (this analysis parses all 136 layers cleanly: own type id, dataId, resolution, dims at fixed offsets, 55-byte header). They power every data-view overlay (pollution, land value, crime, traffic…). A generic SimGridSubfile would be a small, high-leverage parser.
  3. Zone developer / item index (§4.8) — per-tile zoning enables a zoning overlay and is needed before any simulation work.
  4. Region-view completeness — use the localized LTEXT city name (G=0x6AAEE931) instead of the filename; decode the fields still marked unknown in SC4ReadRegionalCity.gd.
  5. Budget/ordinances/graphs (§4.6–4.7) — only needed once simulation or UI panels exist.
  6. Terrain edge strips (0xA9DD6FF4 I=0x64–0x67) — four 129-float strips, almost certainly the neighbour-city edge altitudes used for cross-city edge matching.

Both ARE reachable via raw.githubusercontent.com, which the 2026-07-23 pass did not realise; fetching their source directly is how the §4.4 layouts were established. sc4's src/core/cpp-classes.ts in particular is a type-ID → cSC4* class-name registry and is the fastest way to identify an unknown savegame type. Caveat: neither library is authoritative. SC4Parser's NetworkTile1 mislabels the four 24-byte vertices as three positions plus padding, and sc4's bridge class documents a version-3 layout that does not match the version-2.3 records in the shipped save. Treat both as leads to verify, not truth.

Standard of proof used in the 2026-08-06 revision. A layout was only accepted when a parser written to it consumed exactly the declared record size for every record — not a sample — in every populated save (eight of them). Where that test cannot apply, an independent check was required: foundation and wall placement was confirmed by 100% of centres landing on lot-covered tiles and a median y − terrain of exactly 0.00 m; network-index recovery by the recovered reference count equalling the declared count in all eight cities.

Anything marked Unknown here is, to the best of available community knowledge, genuinely undecoded — SC4's savegame has never been fully reverse-engineered.

7. Session log — 2026-08-06​

Implementing §4.4. Recorded because several findings are not recoverable from the code alone.

Identifications corrected. Three of §4.4's five type IDs were wrong and two subfiles were missing entirely; the table in §4.4 has the detail. The error to learn from: the 2026-07-23 pass inferred 0x49C05B9F/0x49C05C8F/0x49C05C9F from ID adjacency — they sit in the same numeric family as known network types — and adjacency turned out to mean nothing. Two of the three are lot decoration. Record size and shape (700 vs 104 vs 82 bytes; presence of an Exemplar TGI) would have separated them immediately.

Newly decoded.

  • Ground-network record layout, byte-exact — see §4.4. The load-bearing discovery is that SC4 saves the resolved tile: four vertices with position, UV and baked lighting colour, plus the chosen texture id. The RUL tables never need to be evaluated to draw a saved city.
  • Foundation / retaining-wall placement block: f32 x, y, z, size_x, height, size_z.
  • Power lines are two cross-referencing subfiles, spans (0xC9C05C5D) and pylons (0x09C05C6A), joined by memory address. Every span in all five cities that have them names exactly two pylons and both resolve.
  • Pipes lie a median 10.34 m below the terrain surface (range −6.5 to −25.5 m across the 483 records). Consequence for rendering: they cannot be shown by making geometry visible, only by an x-ray pass — see the engine notes below.

Still undecoded after this session. The network index's per-entry payload and the meaning of its tile_number; the ~1.4 KB tail of a power-pole record; the ~390-byte tail of a bridge record (which holds pillar placement, so bridge pillars do not render); the orientation high bit set on 36 ground-network tiles, probably a diagonal-flip flag.

Engine-side findings worth keeping. These bit during this work and are easy to hit again:

  • Network quads must clear the lot base textures, which sit at 0.015 + 0.004 * (priority & 7) — up to 0.043 world units. Anything lifted below that gets buried by a high-priority lot apron, most visibly at intersections.
  • Per-tile quads whose UVs span the full 0..1 of their texture need texture_repeat = false. With the default repeat, edge pixels filter against the texture's opposite edge and leave a hairline seam along every tile boundary.
  • Do not put these quads in the transparent pass. TRANSPARENCY_ALPHA sorts per-object with no depth write, which let lot aprons and the network's own base layer overdraw the road surface; level-crossing tiles vanished entirely. TRANSPARENCY_ALPHA_SCISSOR keeps them in the opaque pass where depth sorting is real.
  • The water shader in City.tscn computed NORMAL as PROJECTION_MATRIX * VIEW_MATRIX * MODEL_MATRIX * vec4(noisenormal, 0). Godot wants NORMAL in view space and a projection matrix is not a valid transform for a direction; the diffuse term collapsed and all water rendered black with only the additive wave highlights showing. Fixed by dropping PROJECTION_MATRIX. Unrelated to networks, but it had been masking the map's water since before this work — a "floating terrain fragment" beyond the map edge turned out to be ordinary land across a bay of invisible water.
  • Water tint still comes from a single texel: texture(watertexture, vec3(vec2(0.0, 0.0), zoom)) paints the whole ocean with the top-left pixel of a 256×256 texture. Sampling with real UVs is a one-line change nobody has made yet.

8. Session log — 2026-08-06 (second pass): 2D sprite props​

Strictly this is a DAT format, not a savegame one; it is recorded here because the save is what leads you to it, and because Core.class_dict had both of its types registered as null — there was no parser to read the code for.

The gap. ExemplarSubfile.get_all_model_refs() finds a prop's model by scanning property values for the S3D type marker 0x5AD0E817. Six prop exemplars used by this save contain no such triple, because they are not 3D objects at all. Every one of their 413 occurrences was counted as "without a resolvable model" and dropped:

Exemplar (G=0xC977C536)InstancesWhat it is
0x28F50000 AStreet1x1x11_stoplightPole_28F333traffic light, orthogonal
0x29E20000 AStreet1x1x11_stoplightPoleDiag_29E29traffic light, diagonal
0x29F00000 / 0x29ED0000 / 0x29EF0000 ARW2x2x5_animatedBallons31balloon bunches on the car lots
0x29C20000 Amill4x2x4_exploritorium_29C20animated crowd of sims

ATC (0x29A5D1EC) — the animation header, reached from the exemplar's ResourceKeyType0 (0x27812820). Group is PROPS_ANIM (0x2A2458F9) for props, NONPROPS_ANIM (0x49A593E7) for everything else. Always exactly 48 bytes, twelve little-endian u32s:

u32Meaning
00x29A5D1EC, own type
1–3FSH type/group/instance — the sprite sheet
40x09ADCD75, AVP type
5AVP group
6–10one AVP instance id per zoom 0–4; 0 where the prop is not drawn at that zoom
11animation rate

Slots 6–10 being per zoom is the load-bearing discovery, and it is verifiable rather than inferred: the filled slots match the exemplar's AppearanceZoomsFlag (0x0ABFC024) bitmask exactly — 0b11100 on the traffic lights, whose filled slots are 2, 3 and 4. Across SimCity_1.dat's 1,084 ATCs only three fill patterns occur at all: zooms {3,4} (1,003 of them), {2,3,4} (79) and all five (2).

AVP (0x09ADCD75) — one zoom's frame table. A 0x24-byte header, verified constant across all 2,253 AVPs in SimCity_1.dat: own type, frame count, two u32 1s, four zero u32s, then the frame count repeated. Frame counts are only ever 8, 4 or 1. Then eight bytes per frame:

ByteMeaning
0page — which FSH directory entry holds this frame
1always 8, in all 15,777 frames
2–3u16 pixel offset of the frame's top-left corner within that page
4–5width, height
6–7anchor x, y — signed int8

Two traps here. The page byte matters because an animation FSH is not one image but up to ~70 directory entries, each a 256×256 DXT1/DXT3 page; FSHSubfile was overwriting self.img per entry and keeping only the last, so multi-page sheets were unreachable. And the offset is a pixel index within its page, so the corner is (offset % 256, offset / 256) — 16 bits covers 256×256 exactly, which is precisely why the page needs a byte of its own.

The anchors really are signed: 9 of the 15,777 frames anchor left of their own rectangle and 2 above it. Read unsigned, those sprites land hundreds of pixels away. No frame is wider than 127 or taller than 126, so the sign costs nothing.

Pixels to world units. A billboard needs a scale and nothing in the ATC/AVP/FSH chain states one. It is recoverable from the S3D data instead: sprites and S3D impostor textures come out of the same pre-renderer, and an S3D vertex carries both a world position and a UV. Least-squares fitting world position -> UV × texture size over ~700 building models per zoom gives the full 2×3 world→screen-pixel matrix. Its row norms, median over the fits, are pixels per 16 m tile:

zoom01234
px per tile6.44912.57624.96556.170112.147

Two things fall out of that fit and are the reason to trust it. The matrix's two rows have equal norm to better than 0.1% — the projection is conformal in the camera plane, which is what makes a single scalar enough to size a billboard. And the matrix independently reproduces SC4's camera: u_x / u_z = 2.4166 ≈ tan 67.5°, and the vertical-to-horizontal ratio is sin 45° at zooms 3–4 and sin 50° at zoom 2 — the azimuth and per-zoom elevations CameraAnchor3D.gd already hardcodes, arrived at from completely independent data. Note the ladder is not a clean ×2: 24.965 → 56.170 is ×2.25. That is measured, not derived; do not "correct" it.

Traffic-light frames are rotations, not signal phases. The stoplight exemplars set "States as Frames" (0x4A70D491), which is easy to read as red/amber/green. It is not: extracting the four zoom-4 frames side by side shows two back views of the pole and two front views with the green lamp lit — they are the four view rotations, the sprite equivalent of an S3D model's four baked rotation variants. So the frame index uses the same expression _place_occupants uses to pick a rotation variant. Whatever drives actual lamp cycling is not in this chain; the exemplar's ResourceKeyTypeMisc (0x27812920) names a second ATC (0x2B2D0000, which does exist, with its own AVPs and FSH) that was not investigated.

Engine-side findings worth keeping.

  • Sprites are camera-facing billboards with vertices emitted relative to the anchor pixel, so the anchor lands on the terrain at the occupant's position. Anything that centres the quad instead leaves poles floating or buried.
  • TRANSPARENCY_ALPHA_SCISSOR, for the same reason §7 gives for network quads — the transparent pass has no depth write and sprites would sort wrongly against buildings.
  • Sprites are hidden at zooms whose ATC slot is empty, as SC4 does, rather than falling back to a coarser zoom's art. At zoom 0 a traffic light is 4 px wide and would be sub-pixel noise on 362 draw calls. Verified by counting lit-lamp pixels down the zoom ladder: 86, 22, 3, 0 at camera zooms 6, 4, 3, 2 — the last being the first unauthored zoom.

Still open. The rate field's unit (read as 1/30 s ticks per frame, which puts the balloons at 0.7 s and the crowd at 1.0 s per frame — plausible, unverified); AVP header u32s 2 and 3, always 1; the second stoplight ATC at 0x2B2D0000; and whether SC4 ever drives a sprite's frame from simulation state, which is what real red/amber/green cycling would require.
